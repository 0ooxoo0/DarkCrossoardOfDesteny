Чтобы подключить приложение-компаньон к игре и не перегрузить основной бэкенд, нужна не просто «ещё одна интеграция», а отдельный, хорошо изолированный слой. Его главная задача — забирать на себя лёгкие и частые запросы, при этом оставаясь безопасным и предсказуемым. Ниже — полная система, собранная из готовых, проверенных решений.

🏛️ Шаг 1: Архитектурный фундамент — паттерн BFF (Backend-for-Frontend)

Не давайте приложению напрямую обращаться к игровым микросервисам или БД. Для этого используется слой BFF — отдельный тонкий сервис, который агрегирует и адаптирует данные именно для мобильного клиента. Он выступает единой точкой входа для приложения, защищая основную инфраструктуру игры.

Как это выглядит на практике (на примере AWS):

· API Gateway (Edge-слой): Принимает запросы, централизованно проверяет JWT-токены, применяет rate limiting и маршрутизирует трафик к нужному BFF.
· BFF-сервис: Легковесный сервис (например, на Lambda или Fastify), который собирает ответ для дашборда, инвентаря или очередей из нескольких внутренних сервисов игры.
· Кэш (Redis / ElastiCache): BFF кэширует агрегированные ответы. Это критически важно для дашборда и кодекса, чтобы не дёргать тяжёлые игровые сервисы по каждому запросу.
· CDN (CloudFront): Для статики (изображения предметов, ассеты кодекса) используется CDN, чтобы разгрузить сеть и ускорить загрузку.

Почему это «умно»: BFF позволяет отдавать приложению именно те поля и в том виде, которые ему нужны, без перегрузки лишними данными. Готовые реализации BFF-слоя можно строить на Fastify (для REST) или Apollo Server (если нужен GraphQL).

🔐 Шаг 2: Аутентификация и привязка аккаунта (OAuth 2.0 + PKCE)

Приложение не должно хранить пароль игрока. Используйте стандартный и безопасный протокол OAuth 2.0 с обязательным PKCE (Proof Key for Code Exchange).

Готовый сценарий:

1. Игрок нажимает «Войти» в приложении.
2. Открывается системный браузер (или WebView) со страницей авторизации вашего игрового аккаунта (или внешнего провайдера, например, Discord).
3. После успешного входа приложение получает короткоживущий Access Token и Refresh Token.
4. Все дальнейшие запросы к BFF идут с этим Access Token в заголовке Authorization: Bearer &lt;token&gt;. API Gateway проверяет его подпись и срок действия.

Готовые решения: Вы можете использовать управляемые сервисы вроде AWS Cognito, Ory или Unity Authentication (с настройкой кастомного OIDC-провайдера).

🔔 Шаг 3: Push-уведомления и Deep Linking (FCM + APNs)

Это ваш главный инструмент для ежедневного ритуала. Сервер должен отправлять уведомления, а приложение — открывать нужный экран.

Готовое решение:

· Транспорт: Используйте Firebase Cloud Messaging (FCM) для Android и Apple Push Notification service (APNs) для iOS. Чтобы не интегрировать два разных API, можно использовать FCM как единую точку входа, загрузив в него ключи APNs.
· Deep Linking (обязательно): В payload уведомления всегда передавайте deep_link или ID сущности, а не только текст. Например: {&quot;deep_link&quot;: &quot;mygame://craft/queue/finish&quot;}. Тогда нажатие на пуш откроет не просто приложение, а конкретный экран с готовым крафтом.
· Готовые обёртки: Чтобы не писать логику для FCM и APNs вручную, используйте сервисы-агрегаторы (например, nitroping), которые предоставляют единый API для отправки пушей на оба платформа и обрабатывают retries и доставку.

⚡ Шаг 4: Real-time обновления (WebSocket / SSE)

Для живых обновлений (например, чат секты или изменение ставок на аукционе) не нужно постоянно опрашивать сервер (polling).

Готовый выбор:

· WebSocket: Идеален для двусторонних сценариев, таких как чат или совместные действия. Вы можете использовать Socket.IO или нативные WebSocket-соединения, которые поддерживаются API Gateway.
· Server-Sent Events (SSE): Отлично подходит для односторонних обновлений от сервера к клиенту (например, лента событий или таймеры аукциона). Это проще в реализации и лучше работает с прокси и балансировщиками, чем WebSocket.

🛡️ Шаг 5: Идемпотентность и безопасность операций

Любое действие, которое меняет состояние (запуск крафта, ставка на аукционе), должно быть защищено от дублирования при повторной отправке.

Готовый паттерн (Idempotency Key):

1. Приложение генерирует уникальный ключ (UUID) для каждой операции и отправляет его в заголовке X-Idempotency-Key.
2. BFF перед выполнением операции проверяет этот ключ в Redis.
3. Если ключ уже есть, возвращается закэшированный результат предыдущего успешного выполнения, а операция не повторяется.
4. Важно: На уровне базы данных также стоит добавить уникальный индекс на поле idempotency_key как «страховку» на случай сбоя Redis.

🏪 Шаг 6: Соответствие требованиям сторов (App Store / Google Play)

Это критический этап, без которого приложение могут просто не опубликовать.

· Guideline 4.2 (Apple): Приложение не должно выглядеть как «сайт в обёртке». Оно обязано использовать нативные возможности: push-уведомления, виджеты, фоновую загрузку, офлайн-режим, биометрический вход. Просто просмотр данных — недостаточно.
· Google Play (Data Safety): Нужно чётко и прозрачно указать, какие данные собираются и как используются, а также предоставить политику конфиденциальности и возможность удаления аккаунта.

💎 Итоговая схема потока данных

В итоге вся система работает так:
Мобильное приложение → CDN (статика) / API Gateway (авторизация, rate limit) → BFF-сервис (кэш, агрегация) → Игровые микросервисы (только необходимые вызовы).
А для уведомлений и real-time: Игровые события → Сервис уведомлений (FCM/APNs + Deep Link) → Приложение, или WebSocket/SSE для живых обновлений.

С чего начать: Возьмите за основу связку API Gateway + BFF + Redis Cache для чтения данных, добавьте OAuth 2.0 + PKCE для входа и FCM/APNs с deep linking для пушей. Этого будет достаточно для безопасного и производительного MVP, который не нагрузит основную игру.

Если захотите детальнее разобрать какой-то из шагов (например, настройку BFF или схему идемпотентности для аукциона), дайте знать.

Коротко: как продуктовый бриф — да, это хорошая основа. Как техническая и операционная спецификация — нет, в плане есть пробелы, которые всплывут на бете или сразу после релиза. Документ отлично отвечает на «что и зачем», но местами слишком поверхностно отвечает на «как именно».

Ниже — что уже хорошо и чего не хватает, чтобы приложение действительно получилось качественным.

Что в плане уже сделано правильно

· Чёткое позиционирование: пульт, а не вторая игра.
· Принцип «сервер — источник истины» и read-mostly.
· Запрет на pay-to-win и эксклюзивную силу.
· MVP из 8 пунктов, а не 10 разделов.
· Отдельный API-слой, кэш, push вместо polling, идемпотентность.
· Понятные метрики и поэтапный запуск.

Это уже отсекает большинство типичных ошибок companion-приложений.

Где план недостаточен

1. Deep linking и push-инфраструктура

Написано «push вместо polling», но не описано:

· как push открывает конкретный экран (крафт → очередь, ставка → лот);
· APNs/FCM, обработка токенов, сегментация, тихие часы;
· что делать, если push пришёл, а данных уже нет;
· стратегия opt-in и защита от notification fatigue (капы, умная частота).

Без deep links push будет вести «куда-то в приложение» — это убивает ценность.

2. Синхронизация и конфликты

«Сервер — источник истины» — верно, но не хватает:

· что происходит, если игрок запустил очередь в игре и в приложении одновременно;
· как разрешаются конфликты офлайн-кэша при возврате сети;
· идемпотентность описана, но нет схемы reconciliation для инвентаря, ставок, вклада;
· как помечается «устарело» и блокируются ли действия на устаревших данных.

3. Виджеты и фоновая синхронизация

Ежедневный ритуал не сработает, если для него надо открыть приложение. Нужны:

· iOS Widget / Android Widget с прогрессом культивации и таймером крафта;
· Live Activities / lock-screen для турниров и аукционов;
· background fetch / WorkManager с учётом лимитов ОС;
· правило: фоновая синхронизация не должна жечь батарею и трафик.

4. Авторизация: краевые случаи

OAuth и короткие токены — мало. Нужно описать:

· мульти-аккаунт и переключение;
· refresh-токены, миграцию устройства, отзыв сессий;
· что видит игрок, если аккаунт забанен или залочен;
· привязку устройства и журнал входов (упомянуто, но без механики).

5. Производительность и бюджеты

Нет цифр:

· время холодного старта (цель, например, &lt;2–3 с);
· размер приложения;
· потребление памяти и батареи;
· поведение на слабой сети (2G/плохой Wi-Fi);
· деградация при недоступном бэкенде (не «белый экран», а кэш + статус).

6. Технологический стек и команда

Не сказано:

· native (Swift/Kotlin) vs cross-platform (Flutter/React Native) и почему;
· кто делает: отдельная мобильная команда или геймдев-команда;
· как шарится код/контракты с игрой (OpenAPI/Proto);
· API versioning: что будет, когда игра обновится, а приложение — нет (force update? graceful degradation?).

7. Магазины и комплаенс

Не упомянуто:

· правила App Store / Google Play (особенно про «пульты» и внутриигровые покупки);
· GDPR/COPPA, согласие на push, удаление данных;
· политика конфиденциальности и хранение токенов (Keychain/Keystore);
· certificate pinning и защита от джейлбрейка/рута — если есть аукцион.

8. Социальный слой: модерация

Чат секты — это не только фича, но и операционная нагрузка:

· модерация, жалобы, теневые баны, фильтры;
· rate limits на сообщения;
· изоляция чата в отдельный сервис (в плане есть), но нет SLA и стоимости.

Без модерации чат быстро превращается в токсичную помойку и головную боль поддержки.

9. Аналитика и атрибуция

Метрики перечислены, но не хватает:

· как связать действия в приложении с удержанием в игре (сквозной user_id);
· A/B-тесты push, экранов, таймингов;
· события для воронки: открыл → посмотрел → сделал → вернулся в игру;
· контроль качества данных (дубли, боты, фрод на аукционе).

10. Локализация и доступность

Не сказано:

· какие языки на старте;
· как хранятся строки и контент (CDN, версионирование);
· доступность: контраст, размер шрифта, screen reader, цветовая слепота.

11. Ошибки и деградация

Что видит игрок, если:

· бэкенд лёг;
· push опоздал;
· ставка не прошла;
· очередь уже завершена в игре.

Нужны шаблоны состояний: загрузка, пусто, ошибка, устарело, нет прав. Иначе приложение будет «ломаться» на каждом сбое.

12. Стоимость и инфраструктура

Не оценено:

· стоимость push, CDN, read-реплик, чата, модерации;
· кто платит за трафик и хранение;
· как это масштабируется при росте игроков.

13. Безопасность аукциона и ставок

«Идемпотентность и лимиты» — мало. Нужно:

· серверная валидация каждой ставки;
· защита от снайпинга и ботов;
· лимиты на аккаунт/устройство/IP;
· логирование и ручной разбор аномалий.

Что добавить в документ, чтобы он стал «достаточным»

1. Раздел «Deep linking и push-стратегия» — с примерами сценариев.
2. Раздел «Синхронизация и конфликты» — с диаграммой состояний.
3. Раздел «Виджеты и фоновая работа» — iOS/Android ограничения.
4. Раздел «Бюджеты производительности» — цифры.
5. Раздел «Технологии и команда» — стек, API-контракты, версионирование.
6. Раздел «Комплаенс и магазины» — GDPR, push-согласие, правила сторов.
7. Раздел «Модерация и поддержка» — чат, жалобы, SLA.
8. Раздел «Аналитика и A/B» — сквозная воронка.
9. Раздел «Ошибки и деградация» — шаблоны экранов.
10. Раздел «Стоимость инфраструктуры» — хотя бы порядок цифр.

Итог

Документ — хороший старт, но для «качественного приложения» его нужно дополнить технической и операционной частью. Самые критичные пробелы: deep linking + push, разрешение конфликтов синхронизации, виджеты/фоновая работа, комплаенс и модерация, бюджеты производительности и версионирование API.

Если закрыть эти шесть зон, план станет не просто брифом, а рабочей спецификацией, по которой можно собрать MVP за 6–8 недель без сюрпризов на бете.

Ниже — практичный план приложения-компаньона (companion app) для игры по «Пику боевых искусств». Главная идея: приложение не должно дублировать игру. Оно снимает нагрузку с основного клиента/сервера за счёт «лёгких» сценариев и усиливает привязку через ежедневные ритуалы, социальность и видимость прогресса.

1. Принципы

· Не заменять игру, а дополнять. Никакого полноценного боя, рейдов и PvP в приложении.
· Read-mostly, write-limited. Основное — просмотр, планирование, очереди, соцсвязь. Записи — только безопасные и идемпотентные.
· Никакого pay-to-win и эксклюзивной силы. Иначе игроки без телефона окажутся в минусе.
· Быстрые сессии. 1–3 минуты: проверить прогресс, запустить очередь, ответить в чате, забрать награду.
· Сервер — источник истины. Клиент не доверяет себе ни прогресс, ни награды.
· Синхронизация прозрачна. Всегда видно, когда данные обновлены и что уйдёт в игру.

2. Что приложение должно снимать с основной игры

· Управление очередями: крафт, алхимия, культивация в офлайне, исследования, тренировки.
· Инвентарь и экипировка: просмотр, фильтры, сравнение, разбор, продажа, но без сложного крафта.
· Планировщик билдов: техники, таланты, формации, сравнение с текущим билдом.
· Секта и фракции: заявки, вклад, миссии, расписание турниров, доска объявлений.
· Аукцион/магазин: просмотр лотов, ставки с лимитами, уведомления.
· Карта и события: где что происходит, таймеры мировых событий, напоминания.
· Кодекс и лор: звери, техники, фракции, легенды, найденные секреты.
· Социальный слой: чат секты, друзья, лидерборды, поиск группы.
· Уведомления: прорыв доступен, крафт готов, аукцион заканчивается, событие началось.

3. Что усиливает привязку

· Ежедневный ритуал: утренний дашборд «что важно сегодня» — 3–5 карточек.
· Видимый прогресс: графики культивации, сравнение «было/стало», цели на неделю.
· Планирование: «до следующего realm’а осталось X», чек-лист ресурсов.
· Социальная принадлежность: чат секты, статусы, достижения, шеринг билдов.
· Ностальгия и коллекции: кодекс, найденные техники, редкие предметы, история персонажа.
· События и календарь: турниры, рейды, аукционы, сезонные активности.
· Push-уведомления по делу: не спам, а «крафт готов», «ставка перебита», «турнир через 30 минут».

4. Чего лучше не делать

· Полноценный бой и рейды в приложении.
· Отдельную экономику и валюту, которая ломает баланс.
· Эксклюзивные награды за установку.
· Сложный крафт, который дублирует игру.
· Постоянный polling сервера.
· Хранение доверенных данных на клиенте.
· 10 разделов на старте.

5. MVP-версия

Сначала только то, что даёт ценность и снижает нагрузку:

1. Авторизация через аккаунт игры.
2. Дашборд персонажа: realm, ресурсы, очереди, ближайшие события.
3. Очереди: крафт/культивация/исследования — просмотр и запуск.
4. Инвентарь: просмотр, фильтры, разбор/продажа с подтверждением.
5. Уведомления: крафт готов, прорыв доступен, событие.
6. Кодекс: техники и ресурсы.
7. Чат секты или друзей.
8. Настройки синхронизации и приватности.

6. Архитектура и снижение нагрузки

· Отдельный API-слой для приложения. Не давайте приложению бить напрямую в игровые БД.
· Read-реплики и кэш. Дашборд, кодекс, карта — из кэша/CDN, обновление по TTL.
· Батчинг запросов. Один запрос на дашборд вместо десяти.
· Push вместо polling. Сервер сам сообщает о событиях.
· Идемпотентные операции. Запуск очереди и ставки — с idempotency key.
· Rate limits и лимиты на действия. Особенно аукцион и чат.
· Серверная валидация. Награды, очереди, ставки — только на сервере.
· Событийная шина. Игра публикует события, приложение подписывается.
· Изоляция соцфункций. Чат и лидерборды — отдельный сервис, чтобы не ронять игру.
· Офлайн-кэш. Последние данные видны без сети, но с явной пометкой «устарело».

7. Безопасность и античит

· OAuth/токены с коротким сроком жизни.
· Привязка устройства и журнал входов.
· Подтверждение опасных действий (продажа, ставка, разбор).
· Лимиты на частоту запросов.
· Никаких наград по клиентскому таймеру.
· Логирование аномалий: массовые ставки, подозрительные очереди.

8. UX/UI

· Тёмная нефритовая/пергаментная тема, как в игре.
· Один экран — одна задача.
· Карточки вместо простыней текста.
· Крупные кнопки для действий, мелкие — для настроек.
· Статус синхронизации всегда виден.
· Уведомления с настройкой по типам и «тихими часами».

9. Метрики

· D1/D7/D30 retention.
· Сколько игроков открывают приложение ежедневно.
· Доля действий, перенесённых из основного клиента.
· Конверсия push в открытие.
· Время до первого полезного действия.
· Крэши, время загрузки, ошибки синхронизации.
· Влияние на удержание в основной игре: возвраты после push, рост сессий.

10. План запуска

1. Собрать MVP на 6–8 недель.
2. Закрытая бета с активными игроками.
3. Замер: снизилась ли нагрузка на основные экраны и вырос ли retention.
4. Добавить соцфункции и аукцион.
5. Только потом — планировщик билдов и кодекс с коллекциями.

Итог: приложение-компаньон должно быть лёгким пультом управления культивацией и социальной жизнью, а не второй игрой. Тогда оно и нагрузку снимет, и привязку усилит — без риска размыть основной геймплей.

Общая структура UI

Лучше делить интерфейс на три слоя:

1. Постоянный HUD — всегда на экране, но минималистичный.
2. Модальные экраны — открываются по кнопке: персонаж, инвентарь, техники, карта, секта.
3. Контекстные панели — появляются по ситуации: диалог, лут, крафт, прорыв, событие.

Визуальный стиль: тёмно-нефритовая или пергаментная основа, золотые/медные акценты, красный — опасность/урон, зелёный — лечение/рост, синий — Ци/дух, фиолетовый — редкие техники. Шрифт — чистый, с «каллиграфическими» акцентами только в заголовках.

---

1. Основной HUD

Зачем: игрок всегда понимает, где он, кто он и что происходит.

Что должно быть:

· Слева сверху: аватар, имя, текущий realm/стадия, полоска Ци.
· Под ней: три компактные шкалы — Тело, Ци, Духовное сознание.
· Сверху по центру: локация, время суток, погода/аномалия.
· Справа сверху: ресурсы — духовные камни, валюта секты, редкий ресурс.
· Справа сбоку: трекер заданий — 3–5 строк, без простыни текста.
· Снизу: хотбар техник 1–6 + предметы, кнопка «Культивировать/Отдых».
· Слева снизу: мини-карта или компас.
· В бою HUD меняется: появляются шкалы врага, статусы, индикаторы дальности.

Как выглядит: полупрозрачные панели с тонкой золотой окантовкой, без тяжёлых фонов. Иконки — нефритовые таблички. Важные предупреждения — красная печать/вспышка, но без постоянного мигания.

---

2. Экран персонажа и культивации

Зачем: это «сердце» игры, здесь игрок видит прогресс и узкие места.

Что должно быть:

· Силуэт персонажа с меридианами/точками акупунктуры.
· Три независимые ветки: Тело, Ци, Духовное сознание.
· Текущий realm, прогресс до следующего, накопленный опыт/Ци.
· «Узкие места»: что мешает прорыву — нехватка озарения, пилюли, ресурса, техники.
· Кнопка «Прорыв» с явным риском: шанс успеха, возможные травмы, цена.
· Дерево озарений/талантов: небольшие узлы, а не огромная паутина.
· Врождённое телосложение/талант с описанием.

Как выглядит: центральная фигура в стиле туши, вокруг — нефритовые кольца стадий. Прогресс — заполняющаяся золотая линия. Опасные действия — красная печать «риск». Никакой мелкой статистики на первом плане: детали — во вкладках.

---

3. Инвентарь и экипировка

Зачем: управление ресурсами, снаряжением и лутом.

Что должно быть:

· Сетка предметов с фильтрами: оружие, броня, пилюли, травы, артефакты, материалы, квестовые.
· Карточка предмета: редкость, описание, эффект, требования, цена.
· Слоты экипировки: оружие, доспех, аксессуар, артефакт, духовный зверь/питомец.
· Быстрые действия: использовать, экипировать, разобрать, улучшить, продать.
· Сравнение с надетым предметом — стрелки вверх/вниз по ключевым параметрам.

Как выглядит: пергаментная сетка, предметы — как талисманы/таблички. Редкость — цвет рамки: серый → зелёный → синий → фиолетовый → золотой. Легендарные предметы — лёгкое свечение и печать.

---

4. Алхимия и крафт

Зачем: закрыть цикл «добыл → создал → усилился».

Что должно быть:

· Рецепты с ингредиентами и количеством.
· Шанс успеха, возможный побочный эффект, качество результата.
· Печь/котёл как визуальный центр экрана.
· Очередь крафта и таймер, если крафт не мгновенный.
· Отдельные вкладки: пилюли, оружие, формации, еда/баффы.

Как выглядит: тёмный экран с котлом в центре, вокруг — слоты ингредиентов. Успех — зелёная печать, риск — красная. Ингредиенты подсвечиваются, если их не хватает. Не прятать шанс успеха в тултип — он должен быть виден сразу.

---

5. Библиотека техник

Зазачем: показать изучение боевых искусств и требования.

Что должно быть:

· Карточки техник: школа, стихия/принцип, ранг, стоимость Ци, перезарядка.
· Уровень мастерства: от «новичок» до «совершенство».
· Требования: realm, духовное сознание, телосложение, учитель.
· Активные/пассивные/защитные/движение.
· Быстрая замена в хотбар.

Как выглядит: свитки или карточки с каллиграфией. Ранг техники — цветом и печатью. Недоступные техники — приглушены, но видны требования. Дерево техник — не обязательное, лучше коллекция карточек с фильтрами.

---

6. Боевой интерфейс

Зачем: бой должен читаться за секунды.

Что должно быть:

· Сверху враг: имя, realm, здоровье, Ци/щит, статусы.
· Снизу игрок: здоровье, Ци, выносливость/тело, хотбар техник.
· Индикаторы дистанции и зоны атак.
· Статусы: горение, яд, кровотечение, оцепенение, баффы — иконки с таймером.
· Подсказка «realm-разрыв»: если враг выше по стадии, показать предупреждение.
· Кнопки: уклонение, блок, рывок, смена стойки.

Как выглядит: минималистично, без огромных панелей. Полоски — тонкие, статусы — небольшие иконки. Урон — цифрами, но без «цифрового дождя». Опасные атаки — красный индикатор на земле.

---

7. Карта и исследование

Зачем: мир должен ощущаться большим, но понятным.

Что должно быть:

· Три уровня: локальная карта, карта региона, карта мира/звёздная карта.
· Туман войны, открытые точки: секты, города, ресурсные жилы, секретные realm’ы.
· Фильтры: ресурсы, задания, торговцы, опасные зоны.
· Быстрое перемещение — только в открытых точках.
· События на карте: случайные встречи, рейды, аукционы.

Как выглядит: старинная карта на пергаменте, тушь, компас, печати локаций. Активные события — пульсирующие красные/золотые метки, но не слишком ярко.

---

8. Секта и фракции

Зачем: социальная прогрессия и доступ к ресурсам.

Что должно быть:

· Ранг в секте, вклад/репутация, текущие обязанности.
· Список миссий: сбор, охота, защита, дуэли.
· Магазин вклада: техники, пилюли, артефакты.
· Список NPC-мастеров и их отношение к игроку.
· Турниры и внутренние соревнования.

Как выглядит: экран как доска объявлений в секте: свитки, печати, иерархия. Репутация — шкала с бронзовыми/золотыми делениями. Важные NPC — портреты в стиле туши.

---

9. Журнал заданий и кодекс

Зачем: не терять сюжет и лор.

Что должно быть:

· Вкладки: сюжет, секта, личные, случайные.
· Цель, награда, рекомендуемый realm.
· Кодекс: звери, техники, фракции, ресурсы, легенды.
· Отметки «новое» без навязчивых восклицательных знаков.

Как выглядит: книга/свиток с закладками. Текст — читаемый, не «каллиграфия ради каллиграфии». Важные термины подсвечены и ведут в кодекс.

---

10. Экран прорыва

Зачем: ключевой момент игры должен быть отдельным событием.

Что должно быть:

· Крупная шкала «шанс успеха».
· Список факторов: пилюли, место, техника, состояние тела, травмы.
· Кнопки «Прорываться» / «Отложить».
· Предупреждение о последствиях провала.

Как выглядит: затемнение, центральная печать/круг культивации, золотые и красные линии. Это модальный экран, а не маленькое окошко.

---

11. Диалоги, магазины, аукцион

Диалоги: портрет NPC, имя, репутация, варианты ответа с последствиями. Стиль — как разговор на фоне свитка, без огромного текстового блока.

Магазины: сетка товаров, цена, репутация, кнопка «купить/продать». Отдельно — вкладка редких товаров за вклад секты.

Аукцион: лоты, текущая ставка, таймер, история. Важно: фильтры и понятная сортировка.

---

12. Уведомления и QoL

Что нужно:

· Тосты: «Получена техника», «Ресурс добыт», «Прорыв доступен».
· Центр событий: офлайн-добыча, завершённый крафт, нападение на секту.
· Настройки: масштаб UI, шрифт, цветовая слепота, переназначение клавиш, отключение экранной тряски.
· Режим «AFK/офлайн»: отдельный экран с отчётом, что произошло без игрока.

Как выглядит: уведомления — небольшие нефритовые плашки справа. Не перекрывать бой. Важные — с золотой печатью, обычные — без звука.

---

Минимальный набор для первого вертикального среза

Если делать не всё сразу, начните с:

1. HUD.
2. Экран персонажа/культивации.
3. Инвентарь.
4. Боевой UI.
5. Библиотека техник.
6. Экран прорыва.
7. Карта.
8. Журнал заданий.

Этого достаточно, чтобы игрок понимал цикл: культивируй → изучай → сражайся → добывай → крафти → прорывайся. Остальные интерфейсы — секта, аукцион, кодекс, турниры — можно добавлять слоями.

Однопользовательская система ИИ для игры по «Пику боевых искусств» — это не только «враг видит игрока и бьёт». Это несколько слоёв: боевой ИИ, ИИ NPC в мире (мастера, торговцы, соперники), симуляция сект и событий, а также ИИ-компаньоны/звери. «По умному» — значит сделать её дешёвой по CPU, предсказуемой, тестируемой и data-driven, а не городить один огромный скрипт.

1. Разделите ИИ на слои

Не смешивайте всё в одном Behaviour Tree.

· Боевой ИИ — тактика в реальном времени: уклонение, выбор техники, позиционирование, отступление.
· ИИ поведения NPC — распорядок дня, реакции на игрока, диалоги, торговля, дуэли.
· ИИ симуляции мира — секты, турниры, войны, рост NPC, события. Работает «в фоне» и не требует покадрового обновления.
· ИИ компаньонов/зверей — следование, поддержка, приказы.

Каждый слой имеет свой бюджет CPU и свою частоту обновления.

2. Боевой ИИ: Utility AI + Behavior Tree

Для боя лучше всего работает комбинация:

· Utility AI выбирает, что делать: атаковать, блокировать, уклоняться, лечиться, использовать технику, отступить. Каждое действие получает «полезность» по формуле от расстояния, HP, Ци, статусов, типа врага.
· Behavior Tree или State Machine выполняет выбранное действие: последовательность шагов, анимации, тайминги.

Почему так: чистое BT плохо выбирает между равнозначными опциями, а чистое Utility AI плохо выполняет длинные последовательности. Вместе — гибко и читаемо.

Готовые решения: Behavior Designer, NodeCanvas, Opsive Behavior Designer, Unity Behavior (новый пакет). Для Utility AI — собственный лёгкий скорер или ассет Apex Utility AI (если есть бюджет).

Практика:

· Все параметры (веса, радиусы, кулдауны) — в ScriptableObject/JSON.
· Не считайте utility каждый кадр: обновляйте раз в 0.2–0.5 с или по событию.
· Ограничьте число рассматриваемых действий (5–8), а не 50.
· Добавьте «анти-тупость»: если действие не удалось N раз — штраф.

3. ИИ NPC в мире: расписания и состояния

NPC не должны думать каждый кадр. Используйте:

· Конечные автоматы (FSM) для базовых состояний: Idle → Patrol → Work → Talk → Combat → Flee.
· Расписание (Schedule) — таблица «время → состояние/место». Утром культивирует, днём торгует, вечером в таверне.
· Событийная реакция — NPC просыпается только когда рядом игрок или произошло событие (нападение, турнир).

Оптимизация: далёкие NPC не обновляются покадрово. Они «спят» и пересчитываются раз в игровой час или при приближении игрока. Это называется Simulation LOD (уровень детализации симуляции).

4. Симуляция мира: тики, а не кадры

Секты, турниры, рост NPC, экономика — это не реальное время, а дискретные тики.

· Мир делится на «чанки» или регионы.
· Активный регион (где игрок) тикает часто; дальние — редко или по формуле.
· Для дальних используйте аналитическую симуляцию: не считать каждого NPC, а прогнозировать результат (например, «секта A с вероятностью 70% победит в турнире»).
· События складывайте в очередь и обрабатывайте порциями, чтобы не было пиков.

Готовые решения: собственный WorldTickManager с приоритетами; для сложных случаев — ECS (DOTS) или Jobs/Burst, но только если реально нужно.

5. ИИ компаньонов и зверей

· Follow/Combat/Support — три режима, переключаемые приказом.
· Компаньон не должен «читать мысли»: используйте blackboard (общая память) и простые правила.
· Для пути — NavMesh + Avoidance; для боя — те же Utility/BT, но с приоритетом «не мешать игроку».
· Ограничьте количество активных компаньонов (1–2), чтобы не плодить сущности.

6. Data-driven и тестируемость

Главная «умность» — не в алгоритме, а в том, что ИИ можно настраивать и проверять без пересборки.

· Все параметры — в ScriptableObject / JSON / Google Sheets.
· Визуальный дебаг: линии агро, текущее состояние, выбранное действие, причины выбора.
· Запись и воспроизведение боя (replay) для разбора багов.
· Юнит-тесты для скорера: «при HP 10% и наличии пилюли — лечиться».
· Симулятор боя без графики: прогон 1000 боёв для баланса.

7. Производительность

· Не используйте Update() на каждом NPC. Централизованный AIManager с очередью обновлений.
· Staggered updates: разносите обновления агентов по кадрам.
· Кэшируйте результаты поиска пути и целей.
· Пулы для снарядов, эффектов, временных объектов.
· Отключайте дальних агентов и анимации.
· Профилируйте через Profiler + ProfilerMarker вокруг ИИ-тиков.

8. Чего избегать

· Один гигантский Update() с кучей if.
· FindObjectOfType и GetComponent в горячем коде.
· Полный пересчёт пути каждый кадр.
· Магические числа в коде вместо данных.
· ИИ, который «знает» всё о игроке без проверки видимости/слуха.
· Симуляция каждого NPC в мире, когда игрок в другом регионе.

9. Готовые решения, которые стоит рассмотреть

· Behavior Designer / NodeCanvas — BT и FSM с визуальным редактором.
· Unity Behavior — новый официальный пакет, если проект на свежей Unity.
· A Pathfinding Project* или NavMesh — для передвижения.
· DOTS/Jobs/Burst — только для массовой симуляции, если реально упрётесь в CPU.
· ML-Agents — не для боевого ИИ, а для офлайн-баланса и тестов (обучение ботов для проверки сложности).

10. Практический план внедрения

1. Сделайте один боевой архетип с Utility + BT и визуальным дебагом.
2. Добавьте Simulation LOD для NPC: активные/спящие.
3. Вынесите параметры в ScriptableObject.
4. Соберите симулятор боя для баланса.
5. Добавьте компаньона с тремя режимами.
6. Только потом — симуляция сект и турниров.

Итог: «умный» однопользовательский ИИ — это слоистая архитектура + data-driven настройка + Simulation LOD + визуальный дебаг + тесты. Алгоритмы (Utility, BT, FSM) важны, но качество даёт не выбор алгоритма, а дисциплина: ИИ должен быть дешёвым, предсказуемым и настраиваемым без переписывания кода.

1. Сильная уникальная фишка

Нужно чётко ответить: чем ваша игра отличается от других cultivation/RPG?
Варианты:

· уникальная боевая система (например, ставка на «разрыв realm’ов» и формации);
· необычная культивация (например, ветки Тела/Ци/Духа реально меняют геймплей, а не только цифры);
· живой мир сект с NPC, которые сами развиваются;
· экономика с аукционом и репутацией;
· тактический бой с позиционированием и стихиями.

Без этого получится «ещё одна игра про культивацию».

2. Проверенный core loop

Должен быть короткий цикл, в который хочется играть сам по себе:
исследуй → сражайся → добывай → крафти → культивируй → прорывайся → открывай новое.

Проверять надо не по списку, а по ощущениям:

· интересно ли уже первые 30–60 минут;
· есть ли реальные решения, а не «нажми кнопку и жди»;
· не превращается ли игра в меню-симулятор.

3. Качественный бой

Это чаще всего слабое место таких игр. Нужны:

· отзывчивое управление;
· понятные анимации и хитбоксы;
· читаемые атаки врагов;
· разные архетипы врагов и боссы;
· ощутимый прогресс: техника не просто «+10% урона», а меняет поведение в бою;
· баланс «realm-разрыва», чтобы высокий враг был опасен, но не неубиваем.

4. Контент, а не только системы

Системы пустые без объёма:

· регионы, подземелья, секретные realm’ы;
· 30–50+ техник с ролями, а не клонами;
· рецепты, ресурсы, звери, фракции;
· сюжетные арки и побочные истории;
· турниры, события, случайные встречи;
· боссы и элитные враги.

Иначе игрок упрётся в «контентную пустоту» через несколько часов.

5. Баланс и экономика

Нужно просчитать:

· темп культивации;
· стоимость прорывов;
· доход ресурсов;
· инфляцию валюты;
· ценность крафта;
· чтобы не было «одной имбы» и мёртвых техник;
· чтобы игрок не застревал в гринде и не проходил всё за 2 часа.

6. Сюжет и персонажи

Для игры по мотивам Martial Peak важны:

· главный герой и его мотивация;
· мастера, соперники, союзники;
· политика сект;
· тайны мира;
· нормальные диалоги, а не только «принеси 10 трав».

7. Арт, звук, UI-полировка

· единый визуальный стиль;
· читаемый UI без перегруза;
· нормальные шрифты и контраст;
· музыка и SFX, которые создают атмосферу;
· анимации, эффекты, обратная связь от действий.

8. Техническое качество

· сохранения;
· стабильность;
· офлайн-режим без потери прогресса;
· производительность;
· управление;
· локализация;
· доступность;
· если есть мультиплеер — античит и серверная логика.

9. Тестирование и плейтесты

Качественная игра — это не только «сделать», но и перебалансировать после тестов.
Нужно проверять:

· не скучно ли на 1-м часу;
· не сложно ли на 5-м;
· не сломана ли экономика на 20-м;
· понятно ли, куда идти;
· не бесят ли таймеры, меню и гриндовые стены.

10. Вертикальный срез

Вместо «сделать всё сразу» лучше собрать кусок:

· 1 локация;
· 3–5 техник;
· 1 цепочка крафта;
· 1 подземелье;
· 1 босс;
· 1 прорыв realm’а;
· сохранение/загрузка;
· 30–60 минут геймплея.

Если этот кусок уже интересен — можно масштабировать. Если нет — список систем не спасёт.

Итог

Ваш список — это дизайн-документ уровня «что должно быть». Для качественной игры к нему обязательно нужны:

· уникальный хук;
· отполированный core loop;
· хороший бой;
· контент;
· баланс;
· сюжет;
· арт/звук;
· техника;
· плейтесты.

Формула простая: качество = системы × исполнение × контент × полировка. Если хотя бы один множитель близок к нулю, игра будет ощущаться сырой, даже если все системы формально на месте.

🧩 Как Addressables решает проблему «мёртвого груза»

Addressables работает на основе подсчёта ссылок (reference counting). Каждый раз, когда вы явно загружаете ассет через Addressables.LoadAssetAsync, счётчик ссылок увеличивается. Когда вызываете Addressables.Release (или ReleaseInstance для инстансов), счётчик уменьшается. Когда счётчик доходит до нуля, система помечает ассет как готовый к выгрузке — но фактическая память освобождается не мгновенно, а когда выгрузится весь AssetBundle, в который входит этот ассет.

Главное правило: каждому Load должен соответствовать Release. Если забыть про Release, счётчик никогда не обнулится, и ресурс останется в памяти навсегда — это классическая утечка.

🗂️ Стратегия группировки: что и как упаковывать

Память освобождается только на уровне AssetBundle, а не отдельного ассета. Поэтому критически важно, как вы группируете ресурсы.

Плохой подход — «одна огромная группа»: если у вас 100 текстур в одном бандле, и вы загрузили одну из них, в память подтянется весь бандл (и все 100 текстур, даже если 99 из них не нужны). Это прямой путь к раздуванию памяти.

Хорошая стратегия — группировка по паттерну загрузки:

· По уровням/локациям: ресурсы подземелья №1 в одном бандле, подземелья №2 — в другом. Игрок в подземелье №1 не держит в памяти текстуры подземелья №2.
· По частоте использования: «общие» ассеты (шрифты UI, иконки, часто используемые VFX) — в отдельный бандл, который живёт долго. Редкие/боссовые ресурсы — в отдельные бандлы, которые грузятся только на время боя.
· По типу: музыка отдельно от SFX, чтобы загрузка нового трека не тянула за собой все звуки ударов.
· Разделение по языкам: если есть локализация, аудио и тексты для разных языков должны быть в разных группах.

Используйте метки (Labels) для пакетной загрузки: Addressables.LoadAssetsAsync&lt;AudioClip&gt;(&quot;music&quot;, null) загрузит все клипы с меткой music одним вызовом.

⚠️ Ловушки, которые создают «пробелы» в оптимизации

Даже с Addressables можно получить проблемы, если не учесть два нюанса.

«Asset Churn» (дёргание ассетов)

Это ситуация, когда вы выгружаете последний ассет из бандла, а затем сразу же загружаете другой ассет из того же бандла. Бандл выгружается и тут же загружается снова — это дорого и вызывает фризы.

Решение: не выгружайте ассеты слишком агрессивно. Если вы переходите из локации А в локацию Б и знаете, что общая текстура (cammo) используется в обеих, не позволяйте счётчику обнулиться. Можно держать «якорную» ссылку на общий бандл, пока игрок находится в зоне, где эти ресурсы могут понадобиться.

«UnloadUnusedAssets» — не серебряная пуля

Метод Resources.UnloadUnusedAssets() действительно может принудительно выгрузить освобождённые ассеты, даже если их бандл ещё в памяти. Но это медленная операция, вызывающая просадки FPS. Её стоит вызывать только на экранах загрузки или в паузе, но не в разгар геймплея.

🧹 Другие техники выгрузки «невидимого» контента

Addressables — основа, но не единственный инструмент. Вот что нужно комбинировать.

Стриминг сцен по расстоянию (для открытого мира)

Для больших локаций используйте трёхсостоянийный жизненный цикл ассетов: Unloaded → Loaded (скрыт) → Enabled. Область вдалеке — Unloaded. Область чуть ближе — Loaded, но скрыта (преload-буфер, чтобы не было «поп-ина»). Ближняя зона — Enabled. При этом выгрузка мешей может происходить по одному в кадр, чтобы растянуть нагрузку. Addressables идеально подходит для загрузки таких «подсцен» асинхронно.

LOD (Level of Detail) + Addressables

Даже если модель видна, её дальняя версия (LOD2) может быть сильно упрощена. Продвинутая техника — грузить разные LOD-ассеты через Addressables в зависимости от расстояния до камеры, выгружая высокодетализированные версии, когда они не нужны.

Пулы объектов (Object Pooling)

Для часто создаваемых/уничтожаемых объектов (снаряды, частицы, всплывающий урон) используйте пулы. Это не про Addressables напрямую, но это снижает «мусор» в памяти и нагрузку на GC, complementая общую стратегию.

Отказ от Resources/ в продакшене

Папки Resources — главный враг оптимизации. Всё, что лежит в Resources, принудительно включается в билд и не может быть выгружено до смены сцены (и то не всегда). Для любого контента, который не нужен «здесь и сейчас», Resources — антипаттерн. Мигрируйте такие ассеты в Addressables.

Direct References — только для действительно постоянного

Прямые ссылки на префабы/ассеты в сцене загружают их сразу и целиком. Это нормально для UI-канвы, главного героя, базовых материалов. Но не для контента, который появляется позже.

✅ Практический чек-лист для вашей игры

1. Аудит: найдите все папки Resources/ и прямые ссылки на тяжёлые ассеты. Решите, что из этого действительно должно грузиться сразу.
2. Группировка: разбейте Addressables-группы по уровням, боссам, типам контента. Избегайте гигантских монолитных групп.
3. Парность Load/Release: введите строгое правило в код-ревью — каждый Load имеет парный Release в том же скоупе (или в OnDestroy).
4. Профилирование: используйте Addressables Profiler Module для отслеживания, что загружено и что освобождено, но ещё висит в памяти из-за бандла.
5. Стриминг для мира: если планируется открытая местность, закладывайте загрузку/выгрузку подсцен через Addressables по расстоянию.
6. Тест на «чёрный экран»: после выгрузки локации проверяйте в профилировщике, что память действительно вернулась к базовому уровню. Если нет — ищите забытые Release или «якорные» ссылки.

Сделать «по умному» — значит выстроить дисциплину: сначала измерять, потом менять, и делать это на уровне архитектуры, а не героических патчей в конце. Вот пошаговый план.

1. Профилируй до того, как оптимизировать

Оптимизация без профайлера — это гадание.

· Собирай Development Build и запускай на целевом железе, а не в редакторе: редактор искажает картину.
· В Profiler смотри CPU/GPU спайки, GC.Alloc и Memory — именно там находятся реальные узкие места.
· Используй Profile Analyzer, чтобы ловить редкие, но болезненные GC-спайки, которые не видны в одном кадре.
· Меняй одну вещь за раз и сравнивай до/после — иначе не поймёшь, что реально сработало.

2. Управляй ассетами через Addressables осознанно

· Каждому Load — парный Release. Addressables считает ссылки; если забыть Release, ассет останется в памяти навсегда.
· Группируй по паттерну загрузки: локация, босс, UI, язык, музыка. Не делай одну гигантскую группу — иначе загрузка одной текстуры подтянет весь бандл.
· Держи зависимости простыми. Если BundleA зависит от BundleB, загрузка ассета из A подтянет и B, даже если он не нужен.
· Следи за Asset Churn: не выгружай и тут же не загружай ассеты из одного бандла — это вызывает фризы. Если ресурс понадобится снова скоро, лучше не отпускать ссылку.
· Выгружай только на экранах загрузки/паузы: Resources.UnloadUnusedAssets() дорогой по CPU и не должен работать в разгар боя.
· Профилируй через Addressables Profiler Module, чтобы видеть, что загружено, что освобождено, но ещё висит из-за бандла.

3. Убери Resources/ из продакшена

Папка Resources — антипаттерн для оптимизации: её содержимое принудительно попадает в билд и плохо выгружается.

· Всё, что не нужно «здесь и сейчас», переноси в Addressables.
· Прямые ссылки оставляй только для действительно постоянного: главный герой, базовая UI-канва, ключевые материалы.

4. Дай миру стримиться, а не грузиться целиком

Для больших локаций в духе Martial Peak используй chunk-based streaming: мир делится на зоны, и загружаются только соседние с игроком.

· Трёхсостоянийный цикл: Unloaded → Loaded (скрыт) → Enabled. Дальние зоны выгружены, ближние — в буфере, чтобы не было «поп-ина».
· Используй квадродерево + LOD-стриминг: дальние чанки грузятся в упрощённом виде, высокодетализированные — только вблизи.
· Выгрузку мешей можно растягивать по одному в кадр, чтобы не ловить просадки.

5. Убей GC через пулы и переиспользование

Каждый Instantiate/Destroy — это аллокация, которая рано или поздно вызовет GC-спайк.

· Для пуль, эффектов, всплывающего урона и часто спавнящихся врагов используй UnityEngine.Pool.ObjectPool&lt;T&gt; или собственный пул на Stack.
· Пул должен иметь стартовую ёмкость и максимальный размер, чтобы память не росла бесконечно.
· Переиспользуй не только GameObject, но и коллекции: List, Dictionary, массивы — их тоже можно пулить.
· В горячих циклах избегай боксинга и лишних строковых аллокаций.

6. Разделяй «загружено» и «активно»

Умная архитектура — это не только выгрузка, но и состояние видимости.

· Объект может быть загружен в память, но выключен (SetActive(false)), пока не попадёт в кадр или радиус взаимодействия.
· Для дальних NPC и объектов используй упрощённую симуляцию (без Update, без анимации), пока игрок не приблизится.
· Не позволяй Update() висеть на сотнях невидимых объектов — это CPU-нагрузка, которую Addressables не лечат.

7. Следи за бюджетом, а не за «красотой»

· 60 FPS = 16.66 мс на кадр; всё, что выше, — уже проблема.
· Держи бюджет памяти на целевое устройство и проверяй его после каждой крупной фичи.
· Ориентируйся на реальные цифры: в кейсах Addressables снижали пиковую память текстур с 480 МБ до 215 МБ (−55%). Это не магия, а следствие управления жизненным циклом.

8. Встрой это в процесс, а не в аврал

· Код-ревью: каждый Load обязан иметь Release в том же скоупе или в OnDestroy.
· Автотест: после выгрузки локации память должна возвращаться к базовому уровню — проверяй снимками Memory Profiler.
· Definition of Done: фича не считается готовой, если она течёт, грузит лишнее или спамит GC.
· Регулярные плейтесты с профилированием на целевом железе, а не «в конце».

Главная мысль: «умно» — это не набор трюков, а цикл: измерил → нашёл узкое место → применил точечное решение → сравнил метрики → закрепил в процессе. Addressables, пулы и стриминг — лишь инструменты внутри этого цикла.

Ниже — по пунктам, как оптимизировать каждый слой, чтобы не потерять качество, но снизить объём работы, риск и «мусорные» фичи. Принцип: оптимизация = не вырезать всё, а сделать систему дешёвой в производстве, гибкой в настройке и понятной игроку.

1. Уникальная фишка

· Выберите один главный хук, а не пять. Например: «бой строится вокруг разрыва realm’ов и формаций».
· Всё остальное подчините ему: техники, крафт, враги, UI.
· Сделайте хук проверяемым в первых 15 минутах.
· Отбросьте фичи, которые не усиливают хук, даже если они «каноничны».

2. Core loop

· Соберите короткий цикл: исследуй → сражайся → добывай → крафти → культивируй → прорывайся.
· Уберите из цикла лишние подтверждения, долгие анимации и пустые пробежки.
· Каждый шаг должен давать быстрый и понятный результат.
· Сделайте цикл повторяемым за 5–15 минут на старте и за 30–60 минут в мидгейме.
· Проверьте: если шаг можно автоматизировать без потери интереса — автоматизируйте (сбор, повторный крафт, офлайн-культивация).

3. Бой

· Начните с 3–5 архетипов врагов и 3–5 ролей техник (урон, контроль, защита, движение, лечение).
· Не делайте 50 техник-клонов. Лучше 20 техник, которые меняют поведение.
· Сделайте читаемые телеграфы атак: цвет, звук, анимация.
· Настройте «realm-разрыв» через понятные правила: урон, пробитие, шанс блока.
· Оптимизируйте производительность: пулы объектов, LOD для эффектов, ограничение частиц, отключаемая тряска.
· Балансируйте не «на глаз», а через таблицы урона/HP/стоимости Ци.

4. Контент

· Используйте модульные куски: локация = набор энкаунтеров + ресурсы + 1–2 секрета.
· Переиспользуйте ассеты и шаблоны: пещеры, руины, секты, жилы.
· Сделайте контентный пайплайн: шаблон квеста, шаблон врага, шаблон рецепта.
· Вместо 100 побочных квестов сделайте 20, но с выбором и последствиями.
· Контент делите на «обязательный срез» и «расширение после тестов».

5. Баланс и экономика

· Вынесите все числа в data-driven таблицы (JSON/CSV/ScriptableObject), чтобы править без пересборки.
· Задайте целевой темп: сколько часов до каждого realm’а.
· Ограничьте источники ресурсов: не больше 2–3 основных способов добычи на ресурс.
· Сделайте «предохранители»: минимальный доход, кап накопления, защита от бесконечной инфляции.
· Регулярно прогоняйте симуляции экономики и боевых формул.
· Уберите «мёртвые» ресурсы: если предмет не используется в крафте/квестах — не добавляйте.

6. Сюжет и персонажи

· Сделайте одну главную арку и 3–5 побочных линий на первый релиз.
· Диалоги пишите шаблонами: реплика, выбор, последствие, награда.
· Не озвучивайте всё — озвучка только ключевых сцен.
· Используйте кодекс для лора, чтобы не пихать его в диалоги.
· Сократите число NPC, но дайте им роль и отношение к игроку.

7. Арт, звук, UI

· Сделайте UI-кит: 1 сетка, 1 стиль рамок, 3–5 цветов редкости, 1 шрифт + акцентный.
· Уберите из UI всё, что не помогает принять решение.
· Оптимизируйте графику: атласы, батчинг, LOD, ограничение прозрачности и постэффектов.
· Звук: 1–2 музыкальные темы на регион, библиотека SFX на действия, без переозвучки каждого удара.
· Проверьте читаемость на маленьком экране и при цветовой слепоте.

8. Техническое качество

· Сначала сделайте сохранения, загрузку, настройки, паузу — без них игра «сырая».
· Офлайн-прогресс считайте на сервере или через проверяемую формулу, а не «доверяйте клиенту».
· Профилируйте узкие места: бой, UI, загрузка локаций, сохранения.
· Ограничьте симуляцию NPC и мира, если она не видна игроку.
· Автоматизируйте сборку и тесты: билд, smoke-тест, проверка сохранений.

9. Тестирование

· Проводите короткие плейтесты каждые 2–4 недели, а не один в конце.
· Смотрите не «нравится/не нравится», а где игроки застревают, скучают, не понимают.
· Записывайте метрики: время до первого прорыва, смертность, доход, использование техник.
· Держите панель баланса: все ключевые числа в одном месте.
· После тестов режьте, а не добавляйте. Оптимизация — это и удаление лишнего.

10. Вертикальный срез

· Соберите 30–60 минут игры: 1 локация, 3–5 техник, 1 крафт-цепочка, 1 подземелье, 1 босс, 1 прорыв.
· Включите туда HUD, инвентарь, боевой UI, экран прорыва и сохранения.
· Не добавляйте секты, аукцион и турниры, пока срез не станет интересным.
· Если срез скучен — масштабирование только увеличит проблему.

Общие принципы оптимизации

· Сначала MVP, потом слои. Не делайте всё параллельно.
· Data-driven вместо хардкода. Числа, техники, враги, рецепты — в таблицах.
· Модульность и переиспользование. Один шаблон — много вариаций.
· Автоматизация рутины. Сборка, тесты, симуляции, отчёты.
· Ограничение scope. Каждая новая система должна заменить или усилить старую, а не просто добавиться.
· Метрики и плейтесты. Оптимизируйте по данным, а не по ощущениям.
· Режьте безжалостно. Если фича не влияет на core loop и хук — она в бэклог, не в релиз.

Итог: оптимизировать нужно не «список систем», а стоимость их производства и настройки. Самая дорогая ошибка — сделать много систем, которые не связаны с core loop. Самая дешёвая оптимизация — сначала собрать вертикальный срез, прогнать плейтесты и только потом расширять то, что реально работает.

Что реально решают Addressables и lifecycle-подход

· Память: не держат в RAM ресурсы, до которых игрок не дотянется.
· Размер билда и патчей: контент можно грузить по требованию и обновлять отдельно.
· Время загрузки: можно грузить только нужную локацию/босса/язык.
· Стриминг мира: подгрузка/выгрузка зон по расстоянию.
· Локализация и аудио: не тянуть все языки и треки сразу.
· Гибкость: можно менять контент без пересборки.

Для игры по мотивам Martial Peak это особенно полезно: много локаций, техник, эффектов, боссов, озвучки, языков. Держать всё это постоянно — плохая идея.

Что это не исправит

· Низкий FPS из-за CPU: физика, AI, скрипты, поиск объектов.
· Draw calls и перегруженные материалы.
· GC-аллокации и фризы от Instantiate/Destroy.
· Плохие алгоритмы, тяжёлые Update, лишние GetComponent.
· Слабый бой, баланс, экономику, контентную пустоту.
· Сетевые проблемы и читы.
· Плохой UI, который сам тормозит.

Где Addressables могут навредить

· Asset churn: выгрузили и сразу загрузили тот же бандл — фризы.
· Утечки: забыли Release, ресурс висит навсегда.
· Фрагментация бандлов: слишком мелкие группы дают оверхед, слишком крупные тянут лишнее.
· Дублирование зависимостей: один и тот же шейдер/текстура попал в несколько бандлов.
· Сложность async-кода: гонки, «пустые» объекты, ошибки при быстром переходе между сценами.

Как понять, что это действительно помогает

1. Сначала профилируйте: Memory Profiler, Addressables Profiler, CPU/GPU профайлер.
2. Найдите реальные пики: память, загрузка, фризы.
3. Внедряйте Addressables точечно под эти пики.
4. Проверяйте метрики до/после: RAM, время загрузки, размер билда, фризы.
5. Тестируйте сценарии: быстрый переход между локациями, возврат в меню, бой с боссом, смена языка.

Итог

Да, это поможет, если:

· есть профилирование и понятные цели;
· группы Addressables собраны по паттерну загрузки;
· каждый Load имеет парный Release;
· есть стриминг и пулы;
· вы не тащите всё в Resources;
· вы измеряете результат, а не просто «внедрили Addressables».

Нет, это не поможет, если:

· вы ждёте, что Addressables сами сделают игру быстрой;
· узкое место не в памяти/загрузке;
· нет дисциплины по освобождению ресурсов;
· бандлы собраны наугад;
· нет плейтестов и профилирования.

Короткая формула: Addressables — это не оптимизация, а инструмент управления жизненным циклом контента. Оптимизация начинается с профилирования и заканчивается метриками.

⚔️ Боевая система

Без этого не будет ощущения «боевых искусств».

· Разрыв в Realm'ах: Жёсткое правило, при котором персонаж низкого realm'а не может нанести значимого урона противнику более высокого realm'а.
· Боевые техники с прогрессией: Изучаемые искусства, имеющие собственные уровни мастерства и предварительные требования (например, уровень духовного сознания).
· Ресурсная боевая система: Энергия/Ци, которая тратится на техники и восстанавливается в бою, а не просто кулдауны.
· Стихийные и концептуальные взаимодействия: Учёт пяти элементов, а на высоких realm'ах — Принципов (Пространства, Времени и т.д.), дающих качественное преимущество.

🏯 Боевые искусства и школы

Это не просто «заклинания», а целые философии и стили боя, часто передаваемые внутри сект.

· Спарринги и реальный бой: В некоторых сектах (как в Павильоне Высокого Неба) практикуются жестокие спарринги, где ученики могут калечить и грабить друг друга. Это делает боевые механики не просто абстрактными, а опасными и ресурсно-затратными.

🔄 Крафт и экономический цикл

1. Добыча: Сбор трав, mining руды, охота на духовных зверей.
2. Переработка: Очистка материалов, создание промежуточных компонентов.
3. Создание: Работа Алхимика, Кузнеца или Мастера Формаций.
4. Улучшение: Повышение ранга существующих артефактов или пилюль (например, через добавление новых материалов).
5. Торговля: Продажа пилюль, артефактов и услуг на рынках и аукционах.

🧩 Формации (Formation Masters / Духовные массивы)

Специалисты по созданию магических массивов (формаций). Они не менее уважаемы, чем алхимики и кузнецы.

Сфера применения:

· Защитные формации сект (Sect Protecting Formations) — как создание, так и разрушение.
· Боевые формации: Часто используются через Formation Plates (Пластины Формаций) — заранее заготовленные массивы, которые можно быстро развернуть в бою.

Уровни: В вики не приводится отдельной лестницы рангов для мастеров формаций, но они, как и алхимики, следуют общей системе культивации (от закалки тела до более высоких царств), а их искусство становится критически важным на высоких уровнях силы.

🧪 Алхимия (Alchemic Dao)

Это основа основ. Алхимики создают пилюли для лечения, прорывов в культивации, усиления, а также яды.

Градация алхимиков (снизу вверх):

1. Common Grade (Обычный)
2. Earth Grade (Земной)
3. Heaven Grade (Небесный)
4. Mysterious Grade (Таинственный)
5. Spirit Grade (Духовный)
6. Saint Grade (Святой)
7. Saint King Grade (Королевский Святой)
8. Origin Grade (Изначальный)
9. Origin King Grade (Король Истока)
10. Dao Source Grade (Источник Дао)
11. Emperor Grade (Императорский) — имеет дополнительное деление Great Emperor (Великий Император).
12. Open Heaven Grade (Открывающий Небеса)

До ранга Dao Source каждая ступень делится на Низкий (Low), Средний (Middle) и Высокий (High) ранги.

Свойства пилюль (качество):

· Normal (Обычные): Стандартные пилюли, чей эффект со временем неизбежно теряется.
· Pill Veins (Пилюльные Вены): На поверхности пилюли есть отметины, похожие на меридианы. Такая пилюля сохраняет свой эффект бесконечно.
· Pill Cloud (Пилюльное Облако): Продвинутая версия Вен. Пилюлю окружает облако, которое постоянно поглощает энергию мира и усиливает её эффект с течением времени.

Особое явление: Grand Alchemic Dao Tone (Голос Великого Дао Алхимии) — шанс услышать прямую лекцию Небесного Дао об алхимии, дающий колоссальные бонусы. Отказ от этих знаний калечит основу культивации.

⚔️ Система культивации (основная шкала силы)

Это скелет всей прогрессии. Она делится на два больших этапа: культивация внутри Вселенной (подчинённая её законам) и за её пределами (превосходящая сами законы). Внутри каждой стадии (кроме поздних) есть 9 малых слоёв (1–9), а поздние стадии делятся на 3 слоя: Начальный / Средний / Пик (Великое Совершенство).

Внутри Вселенной (ранги 1–6):

· 1. Закалка тела (Body Tempering): 9 слоёв. Чисто физическое укрепление. С 4-го слоя появляется ощущение духовной энергии, с 7-го — тело начинает пассивно впитывать Ци (Yuan Qi).
· 2. Начальный элемент (Initial Element / Kai Yuan): 9 слоёв. Ци накоплено достаточно для техник, но его нельзя выпустить из тела — только усилить себя или воздействовать на окружение контактно.
· 3. Трансформация Ци (Qi Transformation / Qi Dong): 9 слоёв. Резкий рост объёма Ци. Энергию можно выбрасывать наружу для атак и защиты, но из-за избытка силы культиватор часто теряет контроль над эмоциями.
· 4. Граница Разделения и Воссоединения (Separation and Reunion): 9 слоёв. Ключевая развилка. В сознании появляются два пути. Если поддаться жажде силы — становятся на «Дьявольский путь» (жестокость, кровожадность). Сильные волей (как Ян Кай) проходят эту стадию без падения.
· 5. Граница Истинного Элемента (True Element Boundary): 9 слоёв. Ци очищается до «Истинной Ци» (True Qi). На этом этапе открывается способность к полёту.
· 6. Граница Бессмертного Вознесения (Immortal Ascension Boundary): 9 слоёв. Важнейший качественный скачок: открывается Море Знаний и появляется Божественное Чувство (Divine Sense) — восприятие окружения без помощи глаз. Именно на этой стадии душа становится отдельной, уязвимой и одновременно атакующей силой.

Переходные / Поздние стадии (ранги 7–8+, часто по 3 слоя):

· 7. Трансцендентный (Transcendent): 3 слоя. Требует постижения части Небесного Дао. Продолжительность жизни выходит за человеческие пределы (сотни лет).
· 8. Трансцендентный Святой (Transcendent Saint): 3 слоя. Истинная Ци очищается до «Святой Ци» (Saint Qi). На 3-м слое большинство может выживать в открытом космосе без защитных артефактов.

Дальше идут ещё более высокие царства (Святой, Святой Король, Возврат к Истоку, Король Истока, Источник Дао, Император), где масштаб силы и «слоёв сопротивления» растёт экспоненциально, вплоть до противостояния законам самой Вселенной.

🎮 Как это можно связать в игровую прогрессию

1. Основная шкала (Культивация): Даёт общий уровень силы, открывает новые «полосы» способностей (полёт, космос) и является «воротами» для контента.
2. Духовная ветка (Чувство/Море): Работает как отдельная «полоса» для ментальных атак, обнаружения скрытого и защиты разума. Слои подавления создают понятные правила PvP/PvE в духовной сфере.
3. Понимание (Просветление): Может быть «скрытой» системой. Игрок не «качает» её опытом, а открывает через события, чтение, медитации или победы над определёнными врагами. Даёт уникальные перки или множители, позволяя «перерасти» свой формальный ранг.
4. Тело/Талант: Это «билд» или стартовые условия. Врождённое тело задаёт вектор развития (танк, поглотитель техник, дуэлянт), а его пробуждение/эволюция становится отдельной сюжетной веткой развития.

💡 Система Понимания (Просветление / Comprehension)

Это то, что отличает «просто сильного» от «истинного гения». Поздние стадии (Трансцендентный и выше) требуют понимания Небесных Законов (Heavenly Laws) — без этого прорыв невозможен.

· Уровни запоминания: Сначала законы заучиваются умом (легко забыть, есть задержка в бою). Затем — телом: доводятся до условного рефлекса, мышечной памяти, которую невозможно забыть.
· Постижение Принципов: На очень высоких стадиях (например, Император) нужно не просто «знать» закон, а напрямую повелевать постигнутым Принципом, конвертируя свою силу в энергию более высокого порядка (Emperor Yuan).
· Влияние на силу: Гений, постигший «пиковые законы» в молодости, может иметь силу, превосходящую его формальный ранг культивации. В игре это может быть скрытый множитель к урону или открытие уникальных способностей.
